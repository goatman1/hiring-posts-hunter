# Inspect Home / For you

Use the existing job-search skill and database. This is an additional collection source, not a separate tracker. Recommendations can surface relevant posts outside keyword results; they do not prove hiring intent, recency, US location or manager authority.

## Scope and counts

Start a run with `collection_source: "for_you"` and `feed_post_count: X` (default 50, range 1–500). X means distinct outer feed post cards inspected in displayed order, including non-hiring, out-of-scope and sponsored cards. Navigation, news/sidebar widgets, comments and embedded reposts do not count as additional cards. Repeated appearances of the same outer post count once per run. Posts seen on previous days still count toward today's inspection budget, but do not become new candidates again.

`target_count`, keywords, author-company search scopes, search sort and date filters do not control this scan. Preserve the recommended ordering. Use max_inspected, max_loading_actions, max_minutes and no_progress_limit as global caps. Report shortfalls instead of endlessly scrolling to find X hiring matches. For combined keyword and feed work, use separate runs against the same data directory and report each run's budget.

## Browser procedure

Count actual posts, not every heading named "Feed post": LinkedIn can use that heading for people-recommendation widgets too. Inspect the author/content and post controls to distinguish them. Recommendation labels such as "X likes this" identify the recommender, not the author.

1. Discover the connected browser and follow its documented interface. Reuse the relevant LinkedIn tab or open Home. Verify **For you** is selected, rather than Network or search results. Record the visible feed ordering and URL in checkpoint progress. The normal entry URL is https://www.linkedin.com/feed/foryou/; verify the page rather than relying on that URL alone. If inaccessible, checkpoint browser_unavailable or authentication_required and report the missing capability.
2. Inspect in display order, batching at most ten outer cards. Use a canonical outer-post ID when visible. If absent, derive a stable fingerprint from the outer author's profile URL and normalized post text, excluding reaction counts, relative age, UI labels and recommendation text. Do not identify a post by the person who liked it, or use a nested original's URL as the outer repost ID.
3. Screen for an actual opening. Classify each card as candidate, not_hiring, out_of_scope or sponsored, with a short reason. Keep minimal IDs/dispositions for unrelated content; do not retain its full body. Sponsored cards count as inspected but are skipped by this workflow. Treat uncertain relevant hiring as candidate so it can receive evidence review. Do not equate any occurrence of "hiring" with an opening.
4. For candidates, expand the full text, capture the outer author's details, displayed date/precision and direct permalink, then build the normal Post record with tech/quant track. Preserve original-post attribution as evidence if this is a reshare. A third-party reshare does not establish the sharer's hiring authority; follow an original source only when useful, retaining both URLs and the relationship. A profile visit is research, not an additional inspected feed card.
5. Submit all inspected cards through **ingest-feed**, including non-candidates, with a stable batch_id. Use zero loading_actions for the initial page; charge each later scroll/load action accurately. Include incremental elapsed_seconds in the batch so an identical retry cannot double-charge time. Check returned counts and stop_reason. Save URL/position/last observed card in checkpoint progress without charging the same time again.
6. Load more using visible controls only. Feed virtualization can remove earlier cards; use saved keys, not current DOM count, for totals. An empty/repeated batch after a loading attempt advances no-progress; a batch of new non-hiring posts is still inspection progress. Do not refresh repeatedly or like/follow/comment to manipulate recommendations. Stop at the requested inspection count, exhausted results, limits, challenges or rate limits.
7. Export a checkpoint, verify candidates against profiles and JDs, then use the normal assessment/worker contract. Saved author facts can be reused if fresh; new own-team and active-hiring claims need post evidence. Inspect old recommended posts for closure rather than treating their appearance today as a fresh vacancy. Preserve unknown dates and unresolved eligibility.

Resume using saved run progress and idempotent batches; feed-audit returns bounded pages of inspected keys/dispositions in rank order. Feed ordering can change, so re-scan cautiously and deduplicate. For a new daily occurrence, start a new run while retaining the same database. An edited candidate keeps its ID and triggers reassessment; contacted/applied/dismissed/closed leads retain their status.

Finish with distinct feed posts inspected, disposition counts, new unique candidates, previously known candidates, verified/shortlisted/review outcomes, source URLs for useful leads, workbook path and actual stop reason. Do not describe a zero-match scan as a failed collection or claim every inspected card was a hiring post.

## Recurring scans — configure later when requested

The repository does not register a schedule. Use Codex's native automation tool when the user requests activation and provides or accepts a cadence; inspect existing automations to avoid duplicates. Prefer a task attached to the ongoing chat unless the user wants standalone runs. Local tasks need the machine/app and connected browser available. A successful manual scan does not prove browser access will exist in an unattended run. Stop and report if login or browser access is unavailable; never install a browser or bypass a challenge.

Use the existing checkout and persistent data directory, not a fresh worktree with an empty tracker. Keep actual local paths and schedule preferences in the automation, not committed personal config. Avoid overlapping scans: continue or checkpoint unfinished work before beginning a second collection, and keep one coordinator writing the database. Do not create a scheduler daemon, model API integration or OS scheduled task.

Reusable prompt (replace the two placeholders before scheduling):

> Use $job-search in <repository path>. Read its For you feed reference and private configuration. Inspect up to <X> distinct LinkedIn Home For you posts in displayed order, including skipped non-hiring and sponsored posts in the inspection count. Use the existing connected browser and the repository's persistent .local database. Start a new for_you run for this occurrence, or recover an unfinished attempt for the same occurrence without starting an overlapping collection. Use ingest-feed in bounded batches, preserve history and deduplicate across searches and earlier scans. Respect configured load/time limits. Verify relevant candidates for US author location, current affiliation, management and own-team hiring, then full-time and junior/PhD-entry role eligibility; match the appropriate resume and save supported drafts. Import tracking edits and synchronize Excel. Report counts, useful new leads, unresolved evidence, workbook path and stop reason. If browser/login access is unavailable, save a checkpoint and report that collection was incomplete. Do not send messages, request connections, upload resumes or submit applications.

Official scheduling requirements: https://learn.chatgpt.com/docs/automations?surface=app. Activation and the first unattended execution must be validated separately from the skill's manual smoke test.
